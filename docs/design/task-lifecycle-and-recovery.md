# 任务生命周期与故障恢复设计

> 状态：规划文档 / 实施前评审
> 范围：首期单机、SQLite、持久化 Worker。本文先冻结设计问题与验收方向，不要求一次性实现复杂调度系统。

## 1. 设计目标

任务状态必须能够准确表达“系统知道什么、已经做了什么、是否可能产生副作用”。服务重启、Worker 崩溃或外部命令超时后，不能仅凭进程退出推断动作未发生，也不能盲目重试非幂等操作。

## 2. 生命周期边界

任务生命周期至少覆盖：创建、调查、计划生成、等待审批、执行、独立验证、完成、失败与恢复。具体状态枚举以核心规格为准；本设计重点补充转换条件和异常路径。

建议明确区分：
- 任务状态：面向用户展示的整体进度。
- Job/Lease 状态：Worker 是否认领任务、租约是否过期、尝试次数。
- Execution 状态：某一次副作用调用是否尚未开始、执行中、已确认完成或结果未知。
- Recovery 状态：是否需要恢复、恢复是否完成、恢复结果是否得到独立验证。

## 3. 必须定义的状态转换规则

每次状态转换应由单一领域入口校验，并将状态变化与审计事件尽可能放在同一 SQLite 事务中。非法转换必须拒绝并留下诊断信息。

设计时逐项回答：
1. 哪些状态允许取消？执行开始后取消代表停止等待、发送终止信号，还是触发补偿操作？
2. 哪些失败可以重试？重试是否会重复产生副作用？
3. 审批后计划、参数、目标或策略版本发生变化时，如何使原审批失效？
4. Worker 租约过期后，旧 Worker 是否可能仍在执行？如何避免新 Worker 与旧 Worker 同时操作？
5. 任务完成的定义是什么：命令退出成功，还是独立验证通过？

## 4. 崩溃恢复与 UNKNOWN

副作用调用存在“命令可能已生效，但结果尚未持久化”的窗口。对此必须显式表达 UNKNOWN / OUTCOME_UNKNOWN（具体名称待核心状态枚举统一），而不是自动回退到待执行状态。

恢复流程建议：
1. 服务启动时扫描过期租约和未终结 Execution。
2. 对只读任务，可按预算和幂等规则重新调查。
3. 对副作用任务，先查询执行记录、目标资源和工具定义的后置条件。
4. 能通过独立观测确认已生效时，进入验证流程；能确认未发生时，才按策略允许重新执行。
5. 无法判定时保持 UNKNOWN，禁止自动重放，交由人工处置或执行专门恢复流程。

## 5. 幂等与重试

每个副作用工具必须声明幂等属性、幂等键策略、可观测后置条件和恢复能力。幂等键不能替代真实的资源状态检查。对不具备安全重试条件的操作，默认不自动重试。

## 6. SQLite 与 Worker 约束

首期单机实现使用数据库事务、条件更新和租约控制任务认领。需要测试 SQLite 锁争用、进程强制退出、事务中断、租约过期、重复认领和重启恢复。暂不引入消息队列或分布式调度器。

## 7. 故障注入验收

- Worker 在认领任务后、开始执行前崩溃。
- 副作用已发生，但 Execution 结果尚未写入数据库时崩溃。
- 命令超时，但目标资源状态已改变。
- 服务重启后租约过期，旧 Worker 与新 Worker 的竞争。
- 审批后参数、目标或策略版本变化。
- 恢复动作失败或恢复后验证不通过。

验收重点：系统不把未知结果伪装成失败或成功；不确定的副作用不会被盲目重复执行；每次恢复判断均有证据和审计记录。

## 8. 暂不纳入

分布式任务调度、多主机协调、跨节点事务、复杂优先级队列和高可用 Worker 均不属于首期范围。
