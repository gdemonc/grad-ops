# Memory 与 Knowledge 设计

> 状态：设计基线。首期以单机运维闭环和完整任务历史为优先；Memory/Knowledge 分阶段落地。

## 1. 为什么要区分

Grad-Ops 需要利用历史上下文，但不同信息的可信度和时效性不同。不能把过去发生过的事当成当前状态，也不能把运维手册当成事实证据。

| 类型 | 回答的问题 | 典型内容 | 可信依据 |
| --- | --- | --- | --- |
| Task History | 系统过去执行过什么？ | 请求、调查、工具调用、审批、执行、验证、审计事件 | 系统自身持久化的事件和结果 |
| Memory | 有哪些值得复用的历史信息？ | 用户明确偏好、环境信息、已验证的历史故障经验 | 可追溯的任务或用户确认来源 |
| Knowledge | 通常应该如何处理？ | Markdown 手册、Runbook、故障处理规范 | 人工维护的文档及其版本 |
| Live Evidence | 主机现在是什么状态？ | 当前磁盘、进程、端口、服务和日志 | 当前任务实时调用只读工具所得 |

## 2. 首期范围

首期不建设复杂的“自动记忆 Agent”。先保证 Task History 完整、可检索、可审计：

- 持久化用户请求、任务状态迁移和时间线。
- 记录每次工具调用的工具名、参数摘要、开始/结束时间、结果状态和输出引用。
- 保存 Evidence 元数据、内容摘要、来源工具和采集时间。
- 关联 Proposal、Action Contract、Approval、Execution、Verification 与 Audit Event。
- 在任务详情中按时间顺序展示过程，支持按任务 ID 查询。

这些记录是后续 Memory 提炼的可靠来源。任务历史中的模型回答不能自动视为已验证事实；需要区分“模型建议”“工具返回”“独立验证通过”和“用户确认”。

## 3. Memory 数据设计（后续阶段）

建议使用 SQLite 结构化存储，不急于引入向量数据库。

### 3.1 记忆类型

- preference：用户明确表达并允许系统复用的操作偏好。
- environment：发行版、服务名、常用目录、端口等环境信息，必须标注采集时间和有效期。
- task_fact：某次任务中经证据支持的事实或结论。
- experience：从多次任务归纳、并经验证的排障经验。

### 3.2 建议字段

memory_items：

- id：唯一标识。
- type：记忆类型。
- content：结构化内容或受控文本。
- source_type、source_id：来源类型及来源记录 ID。
- confidence：可信度或验证状态，不应伪装成精确概率。
- scope：适用主机、服务或任务范围。
- created_at、updated_at、expires_at：生命周期字段。
- status：候选、有效、已过期、已撤销等状态。

可按实际查询需求增加 memory_sources、memory_feedback。首期不必一次性实现关系图谱或复杂版本系统。

### 3.3 写入规则

1. 记忆必须有明确来源；没有来源的模型猜测不得写入。
2. 环境信息需要时间戳和有效期，读取后若影响当前决策，必须重新观测。
3. 与现有记忆冲突时，不静默覆盖；保留来源并标记冲突，必要时请求用户确认。
4. 任务经验必须区分已验证方案、仅尝试方案和失败方案。
5. 用户可查看、纠正或要求不再使用某条记忆。
6. Memory 不具有授权能力，不能改变 Policy、Approval 或 Executor 的约束。

## 4. Knowledge 知识库（后续阶段）

首版知识库使用 Markdown：

- 仓库内维护通用运维 Runbook 和项目规范。
- 每份文档包含标题、适用范围、标签、更新时间和必要的风险提示。
- 检索先采用标题、标签和关键词匹配；结果附带文件路径、段落或行号，方便追溯。
- 文档内容只提供建议和操作说明，不能直接触发工具调用。
- 执行任何建议仍必须转换为已登记工具和 Action Contract，并经过 Policy 与 Approval。

当文档数量、检索质量或语义召回确实成为瓶颈时，再评估 Embedding 和向量检索；不能为了“有知识库”而提前增加独立基础设施。

## 5. 检索与上下文组装

未来任务开始时，按需检索：

1. 与用户明确偏好相关的 Memory；
2. 与目标主机/服务相关且未过期的环境 Memory；
3. 与当前问题相关的历史任务和已验证经验；
4. 对应主题的 Knowledge/Runbook。

检索结果应携带来源和时间，并明确标注为历史信息或文档知识。对于当前状态，仍需调用只读工具生成新的 Live Evidence。上下文应设置数量和长度上限，避免把全部历史记录塞进模型上下文。

## 6. 与 MCP、Kubernetes 的关系

MCP 和 Kubernetes 不属于 Memory/Knowledge 本身。未来若增加外部工具或 Kubernetes 只读能力，应作为 Tool Adapter 接入统一工具注册体系；工具输入输出仍需 schema 校验、权限映射、Policy、Approval、Evidence、Verification 和 Audit。不得因为工具来自 MCP Server 就默认可信，也不得向模型开放任意 kubectl 命令。

这些能力均在单机闭环稳定后再单独设计和评审。

## 7. 分阶段落地

| 阶段 | 内容 | 验收重点 |
| --- | --- | --- |
| 首期 | SQLite Task History、Evidence 引用、完整任务时间线 | 可回放任务过程，来源与执行状态清楚 |
| 后续一 | 结构化 Memory、有效期、来源追溯、关键词检索 | 记忆有来源、过期可识别、冲突不静默覆盖 |
| 后续二 | Markdown Knowledge、标签与关键词检索 | 检索结果可定位原文，不直接授予权限 |
| 后续三 | 经验提炼、反馈、质量评估 | 经验与验证结果关联，支持纠正和撤销 |
| 评估后 | Embedding/向量检索 | 只有在关键词检索不足且有评估数据时引入 |

## 8. 核心约束

**历史帮助理解，知识帮助决策，实时证据反映当前状态，确定性策略决定能否执行。**

这四类职责不可混淆。无论未来接入多少模型、记忆源或外部工具，所有副作用仍必须经过 Grad-Ops 的统一安全执行链。
