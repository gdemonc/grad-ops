# Tool 层安全与 Adapter 扩展设计

> 状态：规划文档 / 首期接口边界  
> 目标：让 Agent 具备真实 Linux Shell 表达力，同时把解析、授权、隔离执行和验证收敛到服务端控制边界。

## 1. 设计原则

Grad-Ops 不应把每一种运维动作都预先封装成固定业务工具。Agent 应能根据实时 Evidence 动态生成、组合 Linux 命令，必要时使用管道、重定向、条件连接和脚本表达复杂操作。

**支持 Shell 语法，不等于无条件信任任意 Shell。** LLM 生成的命令始终是不可信提案；必须经过 Shell AST 解析、语义策略分析、风险判定、动作契约、审批、隔离执行、独立验证和审计。AST 解析不是沙箱，审批也不能把 R4 禁止动作变成允许动作。

## 2. 逻辑分层

```text
User Request
    |
    v
LLM Agent / Planner <-----------------------------+
    |                                              |
    v                                              |
Shell Proposal (script + context)                  |
    |                                              |
    v                                              |
Shell Parser / AST Normalizer                      |
    |                                              |
    v                                              |
Capability + Resource Analysis                     |
    |                                              |
    v                                              |
Policy (R0-R4) -> Approval (when required)         |
    |                                              |
    v                                              |
Sandboxed Linux Shell Executor                     |
    |                                              |
    v                                              |
Evidence / Verification / Audit ------------------+
```

Agent 根据任务逐步提出命令或脚本；每轮执行结果和 Evidence 返回 Agent，由 Agent 决定继续调查、结束任务或提出变更方案。不要让模型一次性生成并执行不可审查的大型脚本。

## 3. Shell 提案与语法支持

提案至少包含原始脚本文本、Shell 类型/版本约束、工作目录、受控环境变量、运行身份、目标资源、超时、输出限制、CPU/内存/PID/文件大小预算、网络策略、预期操作类型、后置条件、验证方式及恢复信息（适用时）。

首期应支持常见运维命令真实需要的 Shell 组合能力：

- 普通命令与参数；
- 管道 `|`；
- stdin/stdout/stderr 重定向（`<`、`>`、`>>`、`2>` 等）；
- 命令序列与条件连接（`;`、`&&`、`||`）；
- 变量/环境变量展开、子 Shell 与命令替换（`$(...)`；反引号形式可先规范化或拒绝）；
- 多行命令与可审查的脚本提案。

例如磁盘排查可组合 `df`、`du`、`sort`、`head`、`find`、`journalctl`，而不必为“查大目录”另写一个固定工具。重定向目标必须纳入资源分析，不能把输出重定向当作无副作用语法。

命令替换、变量展开、子 Shell、循环、函数、复杂条件和多文件脚本均属于目标 Shell 表达能力，不应被永久排除；但每种语法只有在 AST 能递归分析、预算能继承、影响范围能展示且执行环境隔离后才能启用。对 `$(...)` 必须递归分析替换体；反引号应规范化为等价 AST 或明确拒绝。若动态展开生成的命令名/参数无法静态确定，不能自动判为 R0。

## 4. 解析、规范化与能力策略

推荐 Go 使用 `mvdan.cc/sh` 解析 Shell，生成 AST 并进行规范化。解析器只负责语法结构，不提供安全隔离，也不证明命令安全。

服务端维护的是可执行能力与资源策略，而不是每种业务任务的固定工具目录：

- 可执行文件允许列表/拒绝列表、可信路径与二进制身份；
- 命令及参数语义规则、危险选项和动态执行入口；
- 文件/目录资源根、读写权限、重定向目标规则；
- 允许的环境变量、工作目录、运行身份和网络访问策略；
- 语法节点能力、递归深度、AST 节点数和脚本大小限制；
- 单次任务命令数、执行时长、输出量和累计资源预算。

Policy 必须遍历完整 AST，包括管道每个阶段、条件分支、重定向、子 Shell、命令替换和脚本函数体。不能只检查第一条命令，也不能用字符串黑名单代替语法分析。必须特别处理 `eval`、`bash -c`/`sh -c`、`source`/`.`、动态命令名、`xargs`、`find -exec`、`awk system()`、`env` 等间接执行入口。能递归解析的应递归解析并将预算、能力和沙箱约束传递到第二阶段；无法确定实际执行目标的动态命令、未知二进制、未知参数语义、越界路径或策略缺失均 fail closed，禁止自动执行。

## 5. 风险、契约与审批

风险由确定性 Policy 计算，不能采信模型自报等级：

- **R0**：确认只读且资源受限的观测，可按预算自动执行；
- **R1**：低风险、可逆变更，默认审批；只有显式策略可免审批；
- **R2**：影响单个服务或文件的变更，必须人工审批；
- **R3**：高影响动作，默认拒绝或要求额外受限身份与二次确认；
- **R4**：禁止动作，不能通过普通审批放行。

整个 Shell AST 的组合语义决定风险。管道、重定向、条件连接本身不自动等于危险，也不天然安全；例如 `>` 可能覆盖文件，`2>/dev/null` 通常只是丢弃错误输出，而 `find ... -delete` 是明确副作用。必须分析真实命令和目标资源。

审批绑定不可变 Action Contract，至少包括：规范化 AST 摘要、原始脚本摘要、解析器/Shell 版本、所有可执行文件身份、工作目录、环境白名单、运行身份、目标资源、隔离配置、资源预算、风险等级、策略版本和有效期。审批页面展示可读脚本、解析后的命令树、写入/删除/服务影响范围和隔离配置。任何字段变化均重新评估并重新审批。

## 6. 隔离执行

Shell 通过受控执行器启动，不允许 API/Worker 直接拼接字符串调用宿主 Shell。首期最小隔离基线：

1. 专用非 root 执行账号；服务 API 与命令执行账号分离。
2. 使用固定 Shell 二进制和固定启动参数；清理继承环境，设置受控 PATH、HOME、umask、工作目录。
3. 每个 Agent task 使用一个 systemd transient service/scope 或等效隔离单元，施加 CPU、内存、Tasks/PID、执行时间和文件大小限制；同一脚本中的管道阶段共享该隔离单元，不为每个命令单独创建沙箱。
4. 默认限制网络；只挂载任务所需目录，能只读挂载的均只读。可先使用 systemd 的文件系统保护和资源控制；Bubblewrap、Landlock、seccomp 作为按需增强，不要求首期全部引入。
5. 对可用主机启用 AppArmor 或等效 MAC 配置；seccomp/namespaces 作为加固层，不把它们误称为完整容器沙箱。
6. 捕获 stdout/stderr 并限制字节数；超时或超预算时终止整个进程组/cgroup。

若首期无法在目标 Ubuntu 环境可靠启用某项隔离，应明确降级策略和测试结果；涉及高风险写操作时不能在隔离能力缺失的情况下继续执行。绝不以 root 运行任意模型脚本，也不向 LLM 暴露任意 sudo。

## 7. 执行与验证流程

1. Agent 基于任务与 Evidence 生成 Shell 提案。
2. Parser 解析并规范化 AST；拒绝语法错误、超限 AST 或不支持节点。
3. Capability Analyzer 分析所有命令、参数、重定向、动态展开、目标资源及控制流分支。
4. Policy 计算 R0-R4；未知或不可证明安全的路径 fail closed。
5. 生成绑定完整 AST 与执行环境的 Action Contract；必要时请求人工审批。
6. Executor 在执行前重新校验契约、策略版本、审批凭证、二进制身份和隔离配置。
7. 在受限 Linux 执行环境运行脚本，记录退出码、信号、资源使用和截断状态。
8. Verifier 使用新的只读观测检查后置条件；不能仅凭 Shell 返回码认定成功。
9. 结果和 Evidence 返回 Agent 继续规划；所有步骤进入 Execution/Evidence/Audit。

对 `|| true`、管道退出码、后台任务和条件分支必须保留真实失败信息。执行器应配置并记录明确的 pipefail/错误处理语义；不能让脚本通过吞掉错误伪造成功。发生超时、断连或执行器崩溃时，副作用状态记为 UNKNOWN，禁止盲目重放。

## 8. Tool Interface 与 Adapter

接口统一表达 Shell 提案、能力策略、调用上下文、隔离配置和执行结果。首期实现 Linux Shell Adapter；Policy、Approval、Verifier 不依赖 LLM Provider 或具体 Shell 调用方。

未来 MCP/Kubernetes Adapter 必须映射到相同的身份、资源、风险、审批、执行、验证和审计边界。MCP 是接入协议，不是授权系统或沙箱。

## 9. 首期验收

- Agent 可动态组合普通命令、管道、重定向、条件连接和多行 Shell 提案完成常见只读排查。
- Parser 输出 AST；Policy 遍历完整 AST，不使用单纯字符串匹配作为安全判定。
- 未知命令、危险参数、越界读写、未批准副作用和不支持语法均 fail closed。
- 重定向目标、命令替换和子 Shell 的副作用纳入风险与资源分析。
- R0-R4 由确定性 Policy 计算；模型自报风险不能改变结果。
- 审批绑定完整脚本/AST 和执行环境；任何变化必须重新审批。
- Shell 在非 root、受资源限制的隔离环境中执行；超时可终止整个进程组。
- stdout/stderr 截断、退出码、管道失败、资源使用和 UNKNOWN 状态可审计。
- 独立验证使用新的 Evidence；执行结果可关联任务、审批、契约和审计事件。

## 10. 后续扩展与明确边界

后续可逐步开放命令替换、复杂变量展开、循环/函数和更完整的 Bash 语法；每类语法都必须先具备 AST 分析、预算继承、审批展示和隔离测试。不要通过切换成 `sh -c` 就跳过解析与策略。

首期不实现 MCP Client、Kubernetes 操作、多主机执行、动态插件市场、任意提权或以 root 执行脚本。首期可以分阶段启用复杂语法，但最终目标是完整、受控的 Shell 表达能力；不能退化成只允许单条 argv 命令的固定工具菜单。
