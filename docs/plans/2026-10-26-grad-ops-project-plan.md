## 一、项目概述

Grad-Ops 面向 Linux 主机运维场景，计划构建一套具备证据追溯、确定性策略、人工审批、受限执行、独立验证和审计能力的运维控制平面。系统允许用户通过自然语言描述运维问题，由系统执行受限的只读调查、整理证据并形成诊断建议；涉及系统变更时，必须经过动作契约校验、风险策略判定和必要的人工审批，完成后再通过独立观测验证结果。

本项目采用 **Go 作为后端主实现语言，Linux 作为唯一支持平台**。前端沿用现有 Vue 3 技术栈，首期采用 SQLite 保存任务和审计数据，以单机闭环为目标，优先验证系统安全性与可追溯性，暂不实现多主机远程 Agent。

现有 Python 实现仅作为历史行为参考。新版本不逐文件翻译旧代码，而是依据已确认的安全原则重新组织 Go 模块、数据模型、状态机和测试体系。

## 二、项目背景与建设必要性

传统脚本式运维自动化通常依赖固定命令和人工判断，灵活性有限；直接让大语言模型生成并执行命令虽然交互自然，但可能受到提示注入、错误诊断、参数篡改和权限过大的影响。若系统只记录最终回答，也难以说明某项结论依据什么证据、某次变更是否获得授权、操作是否真正成功。

Grad-Ops 计划将自然语言交互与确定性控制机制结合，重点解决以下问题：

1. **诊断依据不透明**：将观测结果保存为 Evidence，并要求结论引用真实证据。
2. **模型输出不可直接信任**：LLM 只能提出调查或动作建议，不能决定最终权限和风险等级。
3. **副作用缺少安全闸门**：所有变更统一经过策略检查、动作契约、审批与受限执行入口。
4. **执行成功难以验证**：执行后重新读取系统状态，验证后置条件；失败时记录恢复过程。
5. **过程难以复盘**：任务状态、审批、执行、验证和恢复事件写入可校验的审计链。

## 三、研究依据与设计原则

本项目的安全架构参考了 LLM Agent 工具使用安全、Agent 应用安全审计、软件工程 Agent 综述，以及 Agent 工作流可观测性与故障注入等研究。相关文献及其工程映射见[《相关论文调研与设计依据》](../research/2026-10-26-related-literature.md)。这些研究用于支撑设计动机和测试思路，不代表 Grad-Ops 已实现论文中的全部方法，也不构成对本项目安全性的实测证明。

据此，项目遵循以下原则：

1. 将模型视为不可信的建议生成组件，策略判定、授权、执行和验证由模型之外的确定性模块控制。
2. 对工具能力、参数、目标资源、信任边界和副作用进行显式登记，并通过危险分析推导可执行的安全约束。
3. 对任务状态、工具调用、审批、执行、验证和恢复建立关联审计，确保关键决策可追溯。
4. 将负向测试与故障注入纳入验收，覆盖提示注入、越权调用、审批重放、Worker 崩溃、执行结果不确定和恢复失败等场景。
5. 以首期可验证的单机闭环为目标，不为追求自主性而提前扩大权限或引入多主机复杂度。

## 四、项目目标

### 3.1 总体目标

完成一个可在 Linux 环境部署、演示和测试的 Go 版单机运维控制平面，形成从自然语言请求到调查、授权、执行、验证和审计的完整闭环。

### 3.2 具体目标

- 建立 Go HTTP API、持久化任务队列和 Worker 执行框架。
- 支持有限的 Linux 只读观测工具，能够采集并保存结构化证据。
- 建立证据绑定机制，阻止结论引用不存在的证据。
- 建立由可信工具登记、参数、目标资源和运行身份驱动的确定性风险策略。
- 建立动作契约、一次性审批凭证和唯一副作用执行入口。
- 支持执行后独立验证，并明确区分执行失败、恢复成功和恢复失败。
- 建立追加式审计事件与 SHA-256 哈希链校验能力。
- 形成 Linux 环境下可复现的单元测试、集成测试和安全测试。
- 保留现有 Vue 3 前端作为工作台，逐步对接 Go REST API。

### 3.3 项目成功标准

项目不以“接入模型”或“能够执行命令”为唯一完成标准，而以安全闭环能否被测试证明为核心：未授权操作必须被拒绝，执行过程必须可追溯，执行结果必须经过独立验证，异常状态不得被错误标记为成功。

## 五、项目范围

### 4.1 首期建设范围

1. **基础服务**：配置管理、日志、HTTP API、健康检查、优雅关闭。
2. **任务管理**：任务创建、状态机、持久化队列、Worker 租约和异常恢复。
3. **只读调查**：磁盘使用、进程、监听端口、systemd 服务状态和 journal 日志等 Linux 观测能力。
4. **模型接入**：支持 OpenAI 兼容接口，并提供可离线测试的 Mock 模式。
5. **证据与结论**：Evidence 持久化、内容摘要、Grounding 与证据引用校验。
6. **策略与审批**：工具登记、风险计算、动作契约、审批状态和一次性凭证消费。
7. **受限执行**：仅开放经过评审和登记的副作用工具，不开放任意 Shell 执行。
8. **验证与恢复**：执行后重新观测，验证后置条件，按明确策略记录恢复结果。
9. **审计**：追加式事件记录、哈希链构建和完整性检查。
10. **前端联调与部署**：Vue 3 工作台接入 Go API，提供 Linux 服务部署方式和测试说明。

### 4.2 首期不包含的内容

- Windows 或 macOS 适配及跨平台兼容层。
- 多主机调度、远程 Agent、远程命令协议和 Agent 自动升级。
- 任意 Shell、任意脚本执行和任意 sudo 权限。
- Kubernetes Operator、分布式事务、主控高可用。
- 未经安全评审的自动化高危变更。
- 将本地哈希链描述为能够抵御完全控制主机或数据库的攻击者。

## 六、总体技术方案

### 5.1 技术选型

| 层级 | 技术方案 | 主要职责 |
| --- | --- | --- |
| 前端 | Vue 3、Vite、现有 UI 组件 | 任务列表、证据展示、审批、执行时间线和审计校验 |
| 后端 | Go、HTTP REST/JSON | API、业务服务、任务编排和状态控制 |
| 持久化 | SQLite、版本化 SQL migrations | 任务、证据、提案、审批、执行、验证与审计数据 |
| 异步处理 | Go Worker、持久化任务队列 | 调查任务执行、租约、超时和故障恢复 |
| 模型接口 | OpenAI 兼容 API、Mock Provider | 生成结构化调查计划与诊断建议 |
| 主机工具 | Linux 固定工具注册表 | 只读观测与有限的受控系统操作 |
| 测试 | Go 单元、集成和安全测试 | 验证业务逻辑、状态迁移与安全边界 |
| 部署 | Linux、systemd、专用服务账号 | 服务启动、权限隔离和运行管理 |

最终 Go 版本、SQLite 驱动和依赖版本应在实施阶段冻结。优先选择部署简单、可在 Linux CI 中稳定构建的方案，避免过早引入微服务和不必要的基础设施。

### 5.2 系统工作流程

```text
用户提交自然语言请求
        ↓
API 校验并创建持久化任务
        ↓
Worker 认领任务并开展只读调查
        ↓
Linux 工具返回观测结果，形成 Evidence
        ↓
LLM 生成结构化分析，Grounding 校验证据引用
        ↓
只读任务：保存结果并封存
        ↓
变更任务：生成动作契约并进行确定性策略评估
        ↓
需要审批？──是──→ 等待人工审批并签发一次性授权
        │
        └─否（仅限明确配置允许的低风险动作）
        ↓
Executor 重新校验契约、授权、参数和资源边界
        ↓
执行已登记的 Linux 操作
        ↓
Verifier 进行新的只读观测并检查后置条件
        ↓
成功封存；失败则按策略恢复并再次验证
        ↓
记录完整审计事件与结果
```

该流程中的模型输出始终属于不可信输入。策略、授权、执行和验证由独立的确定性模块控制。

### 5.3 核心模块

- **API 与任务服务**：处理请求、查询、审批接口，不直接执行系统变更。
- **Worker 与状态机**：管理任务生命周期、超时、租约和崩溃恢复。
- **Investigation 与 LLM Client**：执行有边界的只读调查，限制轮数、工具调用量和总耗时。
- **Evidence 与 Grounding**：保存观测来源和内容摘要，验证结论引用。
- **Policy Engine**：根据可信工具登记、参数、资源和运行身份决定风险与授权要求。
- **Action Contract 与 Approval**：固定待执行动作及参数，绑定策略版本和一次性审批凭证。
- **Executor 与 Linux Tools**：作为唯一副作用执行入口，实施参数、权限、路径和超时限制。
- **Verifier 与 Recovery**：通过新观测检查结果，明确记录恢复是否完成。
- **Audit**：记录状态迁移与安全决策，提供链完整性验证。

## 七、安全设计要求

安全性是本项目的核心验收维度，而不是后续可选优化。

1. **最小权限**：服务默认使用专用非 root 账号；需要特权的能力必须通过独立、范围明确的接口提供。
2. **禁止任意命令执行**：不执行模型生成的 Shell 字符串，使用固定可执行文件和参数数组，不使用 `sh -c` 作为通用执行方式。
3. **默认只读**：调查阶段只暴露已登记的只读工具，副作用工具不得出现在模型可直接调用的调查工具列表中。
4. **风险不可由模型降低**：风险等级由可信工具登记、实际参数、目标资源和运行身份共同决定。
5. **动作不可被静默篡改**：契约摘要绑定工具、参数、目标资源、策略版本和有效期；执行前重新核验。
6. **审批一次性消费**：凭证绑定具体动作，设置有效期，并通过事务保证并发消费不能重复授权。
7. **防护文件系统竞态**：不能仅依赖字符串路径前缀或提前解析符号链接；执行时必须保护实际文件对象，并测试路径替换和 TOCTOU 场景。
8. **执行后独立验证**：验证必须使用新的观测证据，不得直接复用调查阶段的数据证明变更成功。
9. **失败状态准确**：恢复失败进入独立失败状态，不能伪装为回滚成功；动作结果不确定时不能盲目重试。
10. **审计边界明确**：哈希链用于发现链内修改、删除和重排；如需抵御主机 root 或数据库管理员，应进一步引入外部存储或签名检查点。

## 八、实施阶段与进度安排

计划采用阶段交付方式。以下为建议顺序，具体工期应在团队资源、接口和验收范围确认后确定。

| 阶段 | 主要工作 | 阶段交付与验收 |
| --- | --- | --- |
| 阶段 0：规格冻结 | 确认状态机、错误模型、风险等级、动作契约、数据表和 API 契约 | 规格文档定稿，关键规则具有明确测试标准 |
| 阶段 1：Go 基础骨架 | 项目初始化、配置、HTTP 服务、SQLite 迁移、领域模型、Worker | Linux 下可启动；任务可创建、持久化并在重启后恢复 |
| 阶段 2：只读调查 | Linux 工具注册表、LLM Mock/真实接口、调查预算、Evidence 与 Grounding | 只读任务闭环可运行；未知工具和无效证据引用被拒绝 |
| 阶段 3：策略与审批 | 风险引擎、动作契约、摘要校验、审批凭证和原子消费 | 契约篡改、审批过期、重放和并发双消费测试通过 |
| 阶段 4：执行与验证 | 受限副作用工具、Linux 文件边界、独立验证、恢复机制 | 正常、失败、恢复失败及崩溃场景均有明确结果 |
| 阶段 5：审计与交付 | 哈希链、前端联调、部署文档、测试报告和安全复核 | Ubuntu 基线环境中可部署、演示并复现测试结果 |

### 阶段推进原则

- 上一阶段的关键验收未通过，不进入下一阶段的高风险能力开发。
- 先完成 Mock 模式和确定性逻辑测试，再接入真实模型服务。
- 先完成单机安全闭环，再评估多主机扩展。
- 每次阶段交付均更新 README、测试报告和已知限制。

## 九、测试与验收方案

### 8.1 功能测试

- 创建、查询和恢复任务；校验合法与非法状态迁移。
- 采集 Linux 观测数据并保存 Evidence。
- 结论引用真实证据；引用不存在的证据时拒绝或丢弃对应结论。
- 审批、执行、独立验证和恢复流程符合预期。

### 8.2 安全测试

- 提示注入诱导调用危险工具。
- 未知工具、额外参数、错误 schema 和模型自报低风险。
- 动作契约字段篡改、过期审批、审批重放与并发双消费。
- 路径穿越、符号链接逃逸、目录替换和 TOCTOU 竞态。
- Shell 元字符注入、工具超时和超大输出。
- Worker 在执行前后崩溃导致的任务状态不确定与重复执行风险。
- 验证证据复用、恢复失败和审计链篡改。

### 8.3 交付验收标准

1. 项目可在约定的 Ubuntu LTS 环境中构建和运行。
2. Go 单元测试、集成测试、安全测试在 Linux CI 中可复现。
3. 未登记或未经授权的副作用不能执行。
4. 所有执行记录能关联到动作契约、审批状态、执行结果和独立验证记录。
5. 执行失败、恢复成功和恢复失败能够明确区分。
6. 审计完整性检查可以发现受测的事件修改、删除和重排。
7. 部署文档不包含 Windows 运行依赖或 Windows 适配要求。
8. 文档中的功能声明与实际代码、测试结果保持一致。

## 十、主要风险与应对措施

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 重构范围过大 | 开发周期失控，无法形成可演示成果 | 分阶段交付，优先实现单机闭环，暂缓多主机 |
| Go 与旧 Python 行为不一致 | 迁移遗漏关键安全属性 | 以规格和安全测试为准，不以逐文件翻译为目标 |
| LLM 输出不稳定 | 调查流程中断或生成错误结论 | 结构化输出校验、调用预算、重试限制、Mock 测试 |
| 文件系统竞态和权限配置错误 | 造成越权写入或数据损坏 | 安全文件操作、最小权限、故障注入与专门安全测试 |
| SQLite 并发与崩溃恢复问题 | 任务丢失、重复执行或状态不一致 | 事务、租约、条件更新、重启和锁争用测试 |
| 系统工具输出差异 | 解析失败或观测结论错误 | 首期固定 Ubuntu LTS 基线，提供测试夹具并显式记录解析失败 |
| 审计保证被过度理解 | 误认为本地日志能抵御主机完全失陷 | 文档声明信任边界，后续按需要增加外部签名检查点 |
| 前端与后端接口变化 | 联调反复、交付延迟 | 先冻结 API DTO 与错误格式，再开展前端对接 |

1. Go 后端源码与项目结构。
2. Linux 只读工具及有限的受控副作用工具。
3. SQLite schema migrations 和数据模型。
4. 任务状态机、Worker、策略、审批、执行、验证、恢复与审计模块。
5. Vue 3 工作台与 Go API 的联调成果。
6. 单元测试、集成测试、安全测试及 Linux CI 配置。
7. 项目架构文档、核心规格、威胁模型、部署说明和测试报告。
8. 可复现的演示流程：只读调查、审批拒绝、批准执行、验证失败、恢复与审计校验。

## 十二、后续扩展方向

只有在单机版本的安全闭环和故障恢复机制通过验收后，才考虑：

- 多主机 Agent 与安全注册；
- mTLS、命令签名、TTL/nonce 防重放；
- 主控与 Agent 双重策略校验；
- 远程节点独立审计与外部签名检查点；
- 更丰富的 Linux 观测工具与经过评审的运维动作。

上述内容均不属于首期交付承诺，需另行制定协议规格、威胁分析和验收计划。

## 十三、总结

Grad-Ops 的建设重点是把自然语言运维能力限制在一个可验证、可审计、可拒绝的执行框架内。项目以 Go 和 Linux 为统一技术基线，以单机任务闭环为首期目标，围绕“证据可信、策略确定、授权明确、执行受限、结果可验证、过程可追溯”开展实现。

项目将按规格冻结、基础骨架、只读调查、策略审批、受限执行、审计交付的顺序推进。每一阶段均以可复现测试和明确验收标准作为完成依据，避免在核心安全机制尚未稳定前扩张到多主机和高风险自动化场景。
