# Go 版本策略与工具链基线

> 状态：已接受（对应 Issue #7）  
> 适用：本地开发、GitHub Actions、Coding Agent 和发布构建。

## 1. 决策

| 项目 | 版本 | 含义 |
| --- | --- | --- |
| 最低 Go 版本 | **1.26.0** | `go.mod` 的 `go` 指令；模块要求的最低语言/模块语义基线 |
| 开发与 CI 工具链 | **1.27.3** | 日常开发、Linux CI 和验证使用的实际工具链 |

`go.mod` 中的 `go 1.26.0` **不是**“只能使用 Go 1.26.0”。它表示模块的最低兼容版本；使用 Go 1.27.3 构建是正常且当前推荐的方式。

## 2. 为什么不把两者写成同一个版本

- `go` 指令描述的是模块的最低语言版本，也参与语言特性和模块语义的判定。
- CI 需要固定一个可复现的工具链版本，避免 runner 自带的 Go 版本漂移。
- 最低版本和工具链版本是两个独立决策：可以继续支持 1.26.0，同时用 1.27.3 开发和验证。

## 3. 兼容性约束

在最低版本仍为 Go 1.26.0 时：

- 不得引入只有 Go 1.27 才支持的语言特性或标准库 API。
- 不得依赖只在 1.27.3 中存在的工具链行为。
- 依赖升级如果提高了最低 Go 版本，必须按第 5 节处理，而不是直接改 `go.mod`。
- 构建标签、`//go:build`、生成代码和测试都必须能在 Go 1.26.0 下通过。

## 4. 当前验证

2026-11-10 在 Ubuntu 26.04.1 LTS 上执行：

```bash
GOTOOLCHAIN=go1.26.0 go build ./...
GOTOOLCHAIN=go1.26.0 go vet ./...
GOTOOLCHAIN=go1.26.0 go test ./... -count=1

go build ./...
go vet ./...
go test ./... -count=1
go test -race ./... -count=1
```

两套工具链均通过。日常开发和 CI 使用 Go 1.27.3；最低兼容版本由 1.26.0 工具链实际验证，而不是只写在文档里。

## 5. 修改版本的条件与流程

只在以下情况考虑提升最低 Go 版本：

1. 关键依赖要求更高的 `go` 指令，且没有可接受的替代版本；
2. 需要修复的安全问题只能通过新版本标准库/工具链获得；
3. 项目决定停止支持旧版本，并有明确的兼容性评估。

修改时必须：

- 新建 Issue 或 PR，说明原因、影响范围和回滚方案；
- 同时更新 `go.mod`、本文档、`AGENTS.md`、README 和 CI 工作流；
- 用旧版本和新的最低版本分别执行 build/vet/test，记录结果；
- 不得在没有兼容性说明的情况下顺带升级。

提升最低版本不是日常重构的副作用；CI 工具链升级也不能自动改变最低版本。

## 6. CI 与发布构建

- GitHub Actions 固定 `go-version: '1.27.3'`，与本文档一致。
- CI 至少执行 `go build ./...`、`go vet ./...`、`go test ./... -count=1` 和 `go test -race ./... -count=1`。
- 发布构建必须记录实际使用的 Go 版本；最低版本验证和 CI 验证应分别可追溯。
